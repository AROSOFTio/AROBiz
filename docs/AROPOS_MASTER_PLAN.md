Status: planned, 2026-11-26. Release scope is intentionally limited; do not represent planned features as shipped.

## P0 — first production release (blocking)
- Verify independent Crown Docs source copy (tree/checksums), preserve assets and tests; do not copy secrets, signing keys or live data. Separate app ID, backend config and CI credentials for Docs later.
- Restore POS baseline on isolated branch; review diff versus last tested AAB and retain existing data schema, package ID, signing certificate and auth callback scheme until compatibility verified.
- Rename user-facing ARODesk to AroPOS; consistent icon, splash, title, login, receipts, navigation, store graphics; compact blue/white UI, no major workflow rewrite.
- Verify sign-up, sign-in, verification/reset, business creation, session isolation, role restrictions, account deletion and reviewer access. Test with dedicated test tenant, not real customers.
- Verify products, pricing, stock receive/issue, POS cart, cash and recorded payment, credit/debtors, receipt/reprint, quotation/invoice, sales history, dashboard, accounting reports that already exist; fix critical defects only. Hide unsupported or unfinished features. No fake dashboard metrics.
- Offline restart/reconnect tests: durable queue, duplicate prevention, insufficient stock, conflicts, authoritative sync, pending status and tenant-scoped local storage. No silent data loss or double posting.
- Security: inspect RLS and RPC grants, test cross-tenant reads/writes and role enforcement, ensure no service keys in clients. Do not deploy schema changes to live data without backup/staging/rollback.
- CI: flutter analyze/test, clean signed APK/AAB, verify package, manifest versionCode/versionName, certificate against Play upload certificate, target SDK and Play-required compatibility; checksums and release provenance. Test installation and upgrade from previous tested build without data loss.
- Update Play listing to match actual POS features, privacy/data safety, app access, screenshots, content rating, account deletion. User submits only after test evidence. No requirement to finish full ERP before submission; never publish a knowingly defective or misleading app.

## P1 — shared platform and web
Flutter shared domain layer plus adaptive Android and desktop layouts; platform adapters for storage, scanner and printing. PostgreSQL/Supabase shared backend, transactional RPC/API for writes, SQLite local queue and browser storage adapter. Establish staging and production environments, migrations, backup/restore drills, observability and deployment rollback. Web and Android use same tenant identities, business IDs, branches and permissions. Idempotency keys, server revisions, conflict resolution and explicit pending/rejected states; never silently overwrite financial data. Test cross-device sale and stock reconciliation. Web deployment only after browser build and end-to-end tests.

## P2 — modular SaaS foundation
Tables: tenants, memberships, roles, permissions, branches, industry_profiles, module_catalog, module_dependencies, tenant_entitlements, plans, plan_limits, subscriptions, audit_events. Tenant-scoped RLS and server authorization on each request. SaaS admin manages businesses, activation, module catalogue, industry templates, plan and limits, billing configuration, usage and health; no routine access to customer records. Business owner selects available modules, assigns roles and branches. Feature entitlement AND role permission required; disabling a module preserves records, export and dependent financial reports. Free launch: no payment required, enabled entitlements configurable, paid plans disabled until approved. Future billing via compliant platform-specific purchase flows; grace period, read/export access, no destructive suspension.
Onboarding: business name, country/currency, sector, branches, module recommendations, tax setup and opening balances. Sector presets: retail, wholesale, agriculture/agro-dealers, pharmacy commercial inventory, restaurants, hardware, services, manufacturing, general. Owners may customize; no clinical records or regulated dispensing in initial scope.

## P3 — accounting and operational core
Chart of accounts with assets, liabilities, equity, revenue, COGS, expenses; configurable account codes, fiscal periods, opening balances. Decimal monetary values; balanced double-entry journal headers/lines, atomic sale/payment/stock posting, immutable posted entries, reversals, period lock and approval. General ledger, trial balance, balance sheet, P&L, cash flow, AR/AP, bank/cash reconciliation, taxes, audit trail. Inventory movement ledger and consistent costing policy; purchase/receive increases stock, sale decreases stock, return reverses stock and journal. Credit sales/payment allocation and supplier bills. POS barcode, discounts, tax, split payment recording, shifts, refunds and receipts. CRM contacts/leads/opportunities/follow-ups; quotations to orders/invoices; procurement, suppliers, expenses, reporting. Acceptance: balanced journals and stock reconciliation for cash/credit sales, partial payment, returns, purchases, expenses and offline retries; compare known fixture totals.

## P4 — sector and ERP extensions
Retail loyalty and promotions; wholesale bulk price tiers, credit limits and deliveries; agriculture seasonal lots, units and traceability; pharmacy batch/expiry/FEFO and commercial compliance review; restaurant menu/table/kitchen orders; hardware multiple units and quotations; services projects/appointments; manufacturing BOM, production and costing. Multi-branch warehouses/transfers, HR/payroll, fixed assets/depreciation, projects, e-commerce, document templates, SMS/email, imports/exports, payment gateway integrations and regional tax/EFRIS after regulatory validation. Each module ships independently only with migration, API, authorization, UI, tests and documentation.

## Delivery discipline
P0 release first, P1–P4 after approval in increments; no fixed delivery dates assumed. Branch per feature, review, CI, staging, test tenant, migration backup and rollback, signed release notes. Record acceptance evidence and defects in GitHub issues. Critical release blockers: data loss, cross-tenant access, broken login/checkout, wrong accounting, unsigned/wrong identity AAB. Production approval remains Google's decision.
